# Дизайн: закрытие паритета сайта ЛКК ikus.pesc.ru в интеграции eirc_spb

Дата: 2026-09-06. Основа — `docs/parity.md` (паритет-аудит по живому аккаунту).
Структура работ: один спек, пять последовательных фаз; каждая фаза — независимо
выпускаемая версия. Порядок: сначала bugfix и дешёвые атрибуты, затем обогащение
данными, затем история, в конце — самый рискованный PDF-сервис.

Общие принципы:

- все новые вызовы API идут через существующий `EircSpbApiClient._request`
  (авторизация, ретрай при 401, обработка ошибок уже настроены);
- новые данные не должны ломать обновление: любой сбой второстепенного вызова
  логируется, но не валит цикл координатора (как `get_address` сегодня);
- фикстуры тестов снимаются с живого API и обрабатываются штатными
  sanitize-инструментами (`scripts/sanitize_fixtures.py`).

## Фаза 1 — Фикс уведомлений + диагностические атрибуты (2026.9.0)

В этой же фазе — переход на календарные версии в стиле HA
(`год.месяц.патч`): синхронно обновить `manifest.json` и
`const.py:VERSION` (последняя уходит в `User-Agent` и payload сессии).
Последняя семвер-версия — 1.5.2; первая календарная — `2026.9.0`.

### Bug: обязательный параметр `type`

`GET v6/notifications?state=unread&limit=20` (api.py, `get_unread_notifications`)
сервер отклоняет с 500 — `type` обязателен. Фикс:
`v6/notifications?type=bell&state=unread&limit=20` (тип `bell` — лента
«колокольчика», значения enum из фронтенда: MODAL/TOP/BELL/ONBOARDING/EXTERNAL).

### Silent failure

`coordinator._async_update_data` глотает `EircSpbApiError` у нативных
уведомлений. Добавить warning-лог с кодом ошибки, но не чаще одного раза на
уникальный код (предотвращает спам каждые N часов). Поведение fallback
(пустой список) сохраняется.

### Диагностические атрибуты

`v8/accounts` уже отдаёт `autoPaymentOn` и `delivery` — добавить поля в модель
`Account` и показать атрибутами на сенсоре `…_accruals` (у устройств в HA нет
атрибутов; accruals — «главный» сенсор счёта).

### Тесты

- `test_api.py`: точный URL запроса уведомлений;
- `test_sensor.py`: новые атрибуты.

## Фаза 2 — Обогащение из `v7/accounts/{id}/details` (2026.9.1)

### Данные

Один вызов отдаёт: информацию о помещении (адрес, площадь, комнаты, владелец,
УК, проживающие), паспорта всех ПУ (модель, разрядность, дата установки,
**дата поверки**, МПИ, кол-во тарифов), тарифные ставки (капремонт, ТКО,
содержание и т.д.).

### Парсинг

Ответ display-ориентированный:

- блоки электросчётчиков имеют стабильные `code` (`METER_CHECK_DATE`,
  `METER_MODEL`, `METER_DATE`, `CHECK_INTERVAL`, …);
- блоки водосчётчиков кодов **не имеют** — только локализованные `name`
  («Дата истечения поверки») и номер ПУ в заголовке блока.

Парсер: сопоставление по `code`, фолбэк на `name`, привязка к ПУ по серийнику
из заголовка; неизвестные блоки игнорируются. Деградация без ошибок: если поле
не найдено — атрибут просто не появляется.

### Кэширование

Данные почти статичны → кэш на 24 ч по каждому счёту (в памяти координатора,
без persist). Первый цикл после старта — полный фетч.

### Экспозиция

- сенсоры счётчиков: атрибуты `verification_date`, `model`, `install_date`
  (закрывает обещание README: строку «значение пока не передаётся» убрать);
- сенсор `…_accruals`: атрибуты помещения (`area`, `rooms`, `owner`,
  `management_company`) и словарь `tariffs`.

### Тесты

- фикстура `account_details.json` (санитизированная);
- юнит-тесты парсера: блоки с кодами, без кодов, неизвестные блоки;
- тесты атрибутов сенсоров.

## Фаза 3 — Предпроверка показаний (2026.9.2)

`send_meter_reading` перед отправкой вызывает
`POST v7/accounts/{a}/meters/{reg}/scales/{s}/reading/{value}/validate`
на каждое показание (эндпоинт из фронтенда, используется в UI ввода).

- жёсткий отказ → сервис падает с локализованным сообщением сервера
  (вместо сегодняшней генерики);
- мягкое предупреждение («расход больше обычного») → отказ, **если** вызов
  сервиса не передал `confirm: true` (новое опциональное поле, зеркалит
  диалог сайта «вы уверены?»);
- эндпоинт недоступен (404/500) → пропустить валидацию и отправить как сейчас
  (не ломает совместимость).

`api.py`: `validate_reading(account_id, registration, scale_id, value) ->
{status: "ok" | "warning" | "error", message: str | None}`. Схема сервиса:
`vol.Optional("confirm"): bool`.

### Тесты

- моки validate: ok / warning / error / недоступен;
- интеграционный тест сервиса со всеми четырьмя путями.

## Фаза 4 — История счетов и платежей (2026.10.0)

### Новые методы API

- `get_bills_history(account_id, from, to) -> list[str]` (`v7/bills/payments`);
- `get_payments_history(account_id, from, to) -> list[str]` (`v7/payments`);
- `get_bill(bill_id)` (`v8/payments/bills/{id}`): сумма, дата, canDownload;
- `get_payment(payment_id)` (`v8/payments/{id}`): статус, детали, receiptUrl.

### Частота

Окно — 12 месяцев. Фетч истории — раз в сутки по каждому счёту (координатор
хранит время последнего фетча). Первый запуск: до 12 вызовов `get_bill` и
обход верхних `get_payment` до самого свежего по дате (id не хронологичны).
Дальше — только новые id (обычно 1 вызов).

### Экспозиция

- новый сенсор `…_last_payment` (monetary; атрибуты `payment_id`, `date`,
  `status`);
- новое событие `eirc_spb_new_payment` (`payment_id`, `amount`, `date`,
  `number`) — детектор по паттерну `NotificationDetector`, дедуп в памяти
  (как у `new_bill`);
- сенсор `…_bill` получает атрибут `history`: список `{id, amount, timestamp}`
  за 12 месяцев.

### Тесты

- фикстуры: списки id, `payment_{id}`, `bills_{id}`;
- детектор: новый платёж один раз, повторный запуск без дубликата события;
- координатор: суточный троттлинг фетча истории.

## Фаза 5 — Скачивание ЕПД PDF (2026.11.0, спайк-гейт)

### Шаг 0: повторный спайк

Живой ответ: `file: null, canDownload: true` — реальный флоу скачивания
(генерация → `v1/file/{uuid}`?) не проверен. Расширить
`scripts/capture_fixtures.py`, проследить флоу. Если не заработает — фича
отменяется, `docs/parity.md` обновляется, мёртвый код не пишется.

### Сервис (если спайк успешен)

`eirc_spb.download_bill`:

- вход: `entity_id` (сенсор `…_bill`) или счёт + опциональный `bill_id`
  (по умолчанию текущий счёт), опциональный `path`;
- сохранение в `/config/www/eirc/<register>_<bill_id>.pdf` через
  executor (файловый I/O вне event loop);
- валидация пути (без выхода за allowlist), идемпотентность
  (перезапись существующего файла);
- ответ сервиса: `{path, url, bytes}` — для автоматизаций и дашбордов.

### Тесты

- мок API: успешная загрузка, ошибка генерации;
- сервис: путь по умолчанию, кастомный путь, эскейп из allowlist.

## Сквозные решения

- **Ошибки**: второстепенные фетчи (details, history, validate) не роняют
  цикл; лог warning с кодом.
- **Версионирование**: календарные версии в стиле HA (`год.месяц.патч`):
  версия определяется датой релиза, патч — счётчик релизов внутри месяца
  (первый релиз месяца — `.0`). Версии фаз выше — индикативные. При смене
  месяца минорных релизов changelog в README обновляется на релиз.
- **Переводы**: новые поля сервиса — в `strings.json` / `translations/ru`
  (`confirm`, `download_bill`).
- **Вне скоупа**: оплата картой, автоплатежи, отметка уведомлений прочитанными,
  обращение/FAQ, мультипровайдерность.

## Риски

- сервер может изменить/выключить `details`, `validate`, историю — все фазы
  деградируют молча (кроме отправки показаний: сбой validate не блокирует);
- флоу PDF — главный риск, изолирован спайк-гейтом в фазе 5;
- рост числа вызовов за цикл ограничен кэшами (details 24 ч, история 24 ч).
